# UI 设计规范：状态与主操作

本规范适用于涉及异步生命周期、认证、后台进程或网络连接的界面。

## 一个状态，一个主操作

任何有异步生命周期、认证、后台进程或网络连接的 UI，都必须先定义完整状态机，再渲染控件。

### 原则

1. **先列状态，再写 UI。** 禁止用零散布尔值或 `enabled` 开关拼出生命周期。
2. **每个状态只暴露一个主操作。** 同一个状态迁移不能同时由开关、按钮、菜单重复触发。
3. **状态决定文案。** 按钮文字必须直接描述它执行的迁移，例如「启动」「打开登录页」「停止」「重试启动」。
4. **不要把 Switch 用于多阶段生命周期。** Switch 只适合持久化的二元配置；带启动、登录、失败、重试的流程使用「状态 + 主操作」。
5. **次要动作尽量少。** 登录页、刷新状态可以保留为辅助动作，但不得改变主操作的含义。
6. **由单一状态源派生界面。** 例如 `phase: "off" | "starting" | "needs_login" | "running" | "error"`，所有展示和动作都从它派生。
7. **覆盖状态迁移测试。** 至少覆盖每个状态的可见文案、主操作和一次关键迁移；E2E 不只测正常连接。

### 参考状态表：内嵌 Tailscale 网络

| 状态 | 主操作 | 说明 |
| --- | --- | --- |
| `off` | 启动内嵌网络 | 尚未启动 |
| `starting` | 正在启动…（禁用） | 等待网络栈初始化 |
| `needs_login` | 打开 Tailscale 登录页 | 等待用户完成一次授权 |
| `running` | 停止网络 | 已连接 |
| `error` | 重试启动 | 启动失败 |

### 反模式

以下写法禁止再出现：

```text
Switch 开/关             -> 同时控制 start/stop
Switch 显示为开           -> 实际状态是 needs_login / starting
「停止网络」按钮           -> 与 Switch 的 off 重复
多个按钮反复调用同一个 mutate
```

### 评审检查

提交涉及状态 UI 的改动前，逐项确认：

- 状态是否完整列出，是否存在无法到达或无法退出的状态？
- 每个状态是否只有一个主操作？
- 是否存在同一个状态迁移的多个入口？
- Switch 是否真的只表示二元配置？
- 文案是否与当前状态一致，而不是“开了但没连上”？
- 是否有对应 E2E / 单测覆盖中间状态？
